# Assumptions

- Amounts are accepted as positive JSON numbers with at most two decimal places. The service converts them to integer minor units (for example, paise/cents) before storage and calculation, preventing floating-point rounding errors.
- Account and transaction identifiers are UUIDs generated by the service.
- Account balances are never supplied by clients at creation time; the API always initializes them to zero. Requests containing `balance` are rejected with `400 INITIAL_BALANCE_NOT_ALLOWED`, rather than being silently ignored.
- Transactions are immutable. The API intentionally exposes no update or delete endpoints for them.
- A transaction `reference_id` must be unique only within one account, not globally.
- Transfer requests create two immutable transaction records. The supplied transfer reference is suffixed with `:debit` for the source and `:credit` for the destination.
- A page beyond the available transaction history returns an empty `transactions` array together with accurate pagination metadata.
- The default `ledger.sqlite` file is local application state. Set `LEDGER_DB_PATH` for another location or deployment-specific persistent volume.

## Data-integrity guarantees

- Each transaction and transfer uses a SQLite `BEGIN IMMEDIATE` transaction. Account reads, balance validation, balance updates, and transaction inserts occur before the matching `COMMIT`; any error triggers a `ROLLBACK`.
- The schema enforces account primary keys, transaction primary keys, account foreign keys, valid transaction types, positive stored amounts, non-negative balances, and unique `(account_id, reference_id)` pairs.
- Transactions are API-immutable: the service exposes no update or delete endpoint. Database write access is assumed to be restricted to this service.
